Hi there! Sorry I didn't get back to you on the other thread, but I really wasn't certain what angle to come at it from. Having taken it back to basics, you've given me some structure to answer the question.
First off: televisions! Indeed, televisions are able to display images of real life. You may however be underestimating the degree to which even TV, at modern resolutions, has to be compressed for transmission and storage. Without going into too much detail, modern video compression relies a lot on looking for similarities between a given image and the frames around it, and expressing only the differences. Note though that the colour percentage combination stuff works a lot like you suggested, percentage values for red/green/blue. You don't need white or black because the percentages don't need to add up to 100.
Next up: the way you think game engines work: I don't want to say that your conception of game engines is 100% wrong here, as there are engines that work something like what you described. The Myst series, for example, was built out of static pre-rendered images with small video sequences overlaid on it. The earlier Wing Commander games used a set of still images for each ship, and swapped to the most appropriate one for the current viewing angle. Some of the particles in Star Citizen even have short looping animations. However it's absolutely not how most modern games work, for a few reasons that I hope will seem obvious once I've enumerated them:
- Data size: Once again you may be overestimating the processing power and/or storage size available, we just couldn't manage those quintillions of images even if we had something we could do with them. Looking at the memory size of the most recent GPUs (about 12GB), and the size of an uncompressed full-screen image (1920  1080  3(bytes) / 1024^2(bytes in a MB) = 5.9MB), you're looking at maybe a few thousand frames of uncompressed data, if you're going to let the player get up close to them.
- Getting up close: Your cube example doesn't have so much trouble with this, but suppose the cube is a ship. What happens when the player tries to climb inside something that only exists as a 2D video?
- Lighting: As you may have noticed, ships can't just be viewed from multiple angles, they can be lit from any angle too, by multiple lights. It's theoretically possible to store the info you'd need for that in a series of videos, something like the scheme you described, just have extra channels for the surface direction, the shininess, maybe one for any glowing parts, and so forth. But this is just inflating an already impossible problem into an even more impossible one.
How (most) engines actually work: If you look at point 3 above, you might consider that storing surface colour, direction, shininess, glow, etc, might be more manageable if you just had to store a single image instead of a video. Game objects in Star Citizen, and most other engines, are stored in memory as a set of triangles that define the 3D position of each corner, and the location on a 2D image that this corner should match up to (plus a few extra things I won't get into). For any frame, the engine can say "draw list-of-triangles A with 3D transformation B", and the graphics hardware executes a program on each triangle vertex to place it in the correct place, then colours in the space inside the triangle, executing a program for each pixel that can do things like fetching the 2D image, calculating lighting, etc.
To achieve something like your Rubik's Cube, we'd send off 26 different transformations, one for each of the sub-cubes. There'd be nothing constraining them to even be near each other, but the game code would enforce that.
Doing it all on a 3D grid: Some games do this! Sort of. Generally, it's still faster to submit triangle meshes to the GPU, but some people store a grid of values similar to the one you described, for doing things like landscapes, or for scenery that they want the players to be able to modify. In the end that's just another choice of storage format, though as I understand, it takes a lot of effort to keep it efficient. Also it's worth mentioning that if something moves, it's generally required that the moving object has its own grid, since otherwise every time an object moved in some way that didn't perfectly line up with the grid cells, it'd blur slightly, and quickly reduce to mush.
Ok, that was a longer answer than I expected. Hopefully it shed some light on how we really do things?
